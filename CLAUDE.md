# indoor-generator

Generates Mapbox indoor maps (facility/structure/floor/room GeoJSON, Mapbox indoor data model) for real buildings from a
natural-language request: OSM footprint + web research → `configs/<slug>.json` → Python
pipeline → `output/<slug>/indoor.geojson` + live preview, then refined through conversation.

**For any request to create or change an indoor map, use the `indoor-map` skill**
(`.claude/skills/indoor-map/SKILL.md`).
Its follow-ups are separate skills, loaded only when needed: `indoor-floor-image` (overlay / align / trace a floor-map image),
`indoor-importer` (new floor-guide site importers), `indoor-quality` (sourcing grades, `report` / `compare` / `cost`),
`indoor-publish` (tileset upload; only when the user asks).

Official Mapbox skills vendored from [mapbox/mapbox-agent-skills](https://github.com/mapbox/mapbox-agent-skills)
(MIT, commit `f71cd72`; `SKILL.md` + `references/` only — update by re-copying, don't edit in place):
- `mapbox-data-visualization-patterns` — when changing GL JS layers/expressions in `templates/preview.html` (fill-extrusion, feature-state)
- `mapbox-web-performance-patterns` — preview load time, `setData` reloads, large GeoJSON
- `mapbox-token-security` — anything touching how the token is passed to / embedded in `index.html`

  `report` (how well each room is sourced: traced / listed / estimated / derived, per floor, and the weakest rooms to research next; also a footprint-overlap check (per floor, the share of the traced area inside the footprint and the rooms mostly outside it; `quality.footprint_check`; rooms are never cut to it, it only says how well the floor map and the footprint agree), a listed-vs-built check (the tenants a source lists on a floor, `metadata.tenants_listed` of its plan, written by the importers and `main.py trace --listed N`, against the shops built from a source shape; `quality.listing_check`) and a stacking check, `indoor_gen/stacking.py`: do the lifts / stairs / escalators of neighbouring floors sit on top of each other, or is a floor map shifted as a whole; it needs 2+ shafts that agree, so it only confirms or flags, e.g. 丸ビル 1F-6F stack, while 東京駅 B1F-1F has too few shafts to tell),
  `compare` (two builds of one building, e.g. per model: cost, sourced share, alignment, room/category agreement)

A new UI text is written in English and needs its `ja` entry — `tests/test_preview_i18n.py` checks it). The preview has one layout for viewing and editing: a top bar (floor, "Edit floor"), the facility (name, building picker, live dot), a "Display" section with the source-data comparison and tabs (Legend / Source / History) on the left, the selected room and the floor's rooms on the right; the edit mode keeps the left and swaps the right for the tool details + Table / JSON), `server.py` (SSE live reload, selection; serving `/` first re-renders a page older than `preview.html` from the new template, keeping its data — `build_preview.refresh`)

- `indoor_gen/recipe.py` + `recipe_cli.py` — `main.py recipe <slug> [--fetch] [--record]` makes a building's third-party floor-map images (`configs/plans/<slug>/maps/*.png`, git-ignored) again from `configs/plans/<slug>/recipe.json`: sources (URL, sha256; cached under `output/<slug>/sources/`), per image the ops (`pdf_page`, `crop`, `resize`) and its pixel hash, plus the commands that made the plan data as `steps` (documentation only). `--record` writes the hashes while authoring; exit code 1 when an image no longer matches.
- `indoor_gen/auto.py` + `auto_cli.py` — `main.py auto <slug> [--dry-run] [--only S] [--start S] [--force] [--fetch]` runs a building's stages from its `recipe.json`: images → each step with a `cmd` (`inputs` / `outputs` paths; run through this Python from the repo root) → `build` → `check`. State in `output/<slug>/auto/state.json` (key = hash of command + inputs): an unchanged stage is skipped; an output that exists but was never run by `auto` is adopted, not overwritten, and one edited by hand since the last run is left alone (`--force` overwrites) — the tools overwrite their output, which would drop pictograms added later. A step without `cmd` is manual (listed under `review` until its `outputs` exist; `optional` keeps it off). `check` reads the build and lists what to look at: weak sourcing, traced area outside the footprint, floor maps placed by outline only (no landmark alignment). The result's `review` is the list for a person
- `indoor_gen/orient.py` + `orient_cli.py` — `main.py orient <config> --level N` says which way a placed floor map is turned: the four quarter turns of its placement are scored by how well the names printed on the map (named zones of the floor's `*-trace.json`) land on OSM features of the same name (`fetch_building.named_places`, cached in `output/<slug>/osm_names.json`); `clear` needs 2+ names, a median under 60 m and under half of the next turn's, else `undecided` (then read a compass or landmark). `turn_deg` is how far to turn it clockwise from now (0 = keep). `auto`'s check stage shows it from the cache; `report` and `quality.json` carry `placement` (`quality.placement_basis`: landmarks with pairs / rms, or the footprint outline only)
- `indoor_gen/geojsonio.py` — round trip through geojson.io: `main.py export-floor <config> --level N` (or the edit mode's "Export", `GET /floor-export`) writes the floor's rooms (`id` = config room id, `name`, `category`); `import-floor <config> --file <edited> [--dry-run]` (edit mode: "Import", `POST /floor-import`) diffs it against the build: changed shape / name → `update`, no `id` + `name` → `add`, missing → `delete`, then `edit-rooms`' path (`room_edit.apply_edits`) and build. Vertex-level edits only; image alignment / nudge stay in the preview
- `indoor_gen/realign.py` — `main.py nudge-map <config> --rotate-deg / --scale / --east-m / --north-m [--level N]` moves every plan and floor map (with `--level`, only that floor's plan, outline and map) (and, with `building.footprint_follows_map: true` — a footprint and floor `outline`s drawn from the floor maps, e.g. Haneda T2 — the footprint and outline files too) by a small hand-set amount (rotation counter-clockwise about the footprint's centre) when the fit needs a last touch; the preview's edit mode ("Edit floor" → the "Floor map" mode) has a rotation slider and drag (drag the map, scale with the corner / edge handles; scale 0.2–5×, shifts ±1000 m), `POST /nudge`: the shown floor map moves live; "Save this floor only" moves that floor's plan and map (`level`), "Apply to all floors" every floor
- `indoor_gen/align.py` — image corners from point pairs (`output/<slug>/alignment.json`, saved by the preview);
  A floor map is never bent to the footprint: `align.auto_fit` (used by `main.py basemap`; `--map-up` / `--north-deg` (a north arrow's angle, any value) / `--like-level` fix which way is up, a near-symmetric building is reported as ambiguous) only scales, turns and moves it so the drawing's outline covers the footprint (IoU); `--true-width-m <printed width>` fixes the drawing's real size (it is then only turned and moved), for a footprint that is not the building's real size (OSM still holding the pre-construction building); point pairs are `similarity` only
  `indoor_gen/crop.py` — on build the shown floor-map image is trimmed to the floor's extent + a small margin (legend / blank
  margins out); the full image stays as `source_url` for alignment, the trimmed rect is `crop_px` in the metadata
- `indoor_gen/quality.py` (sourcing grades) and `indoor_gen/compare.py` (two builds of one building) back `report` / `compare`
- `indoor_gen/georef.py` — fit a floor-plan drawing onto the footprint; `indoor_gen/importers/` — site importers

## Footprint policy
The building's footprint is the OSM outline (an `osm_id` source; the way is also how the building is located). Where OSM holds the old building or a coarse shape, the footprint is drawn from the building's own floor plan (its outer wall at real scale) or from the shops traced on the floor maps (their union, courtyards filled in), written as `plans/<slug>/footprint.geojson`. **Never take a shape from Mapbox's tiles (Mapbox Streets, the Mapbox Building), and never store or publish one**: the Mapbox Product Terms forbid tracing, deriving or extracting content from the service (1.6), caching or storing it (1.9) and redistributing it (1.10). The preview may be drawn over the Mapbox basemap (that is using the service); the indoor data must not contain a shape copied from it. A footprint is never redrawn from a schematic that is not to scale, and traced plan rooms are never dropped or clipped for lying outside it: they stick out, and the floor slab / wall follow them (the `trace` output reports the share inside). Floor `outline`s drawn from a floor map are optional and carry `properties.follows_map: true` so `nudge-map` moves them with the maps (`building.footprint_follows_map: true` is only for a footprint that is itself drawn from the maps). `build` and `publish` warn about a footprint that an older build extracted from Mapbox Streets (`footprint_source: mapbox`).

## Spec references
- [Indoor mapping guide](https://docs.mapbox.com/help/dive-deeper/indoor-mapping/) — the spec for authoring custom GeoJSON (`type` = `facility|structure|floor|room`, walls are `type: room` + `class: wall`)
- [Mapbox indoor-v3 tileset reference](https://docs.mapbox.com/data/tilesets/reference/mapbox-indoor-v3/) — Mapbox's own published tileset (layers, `class` / `icon` vocabulary); check it first for any `class` question
- [Build an indoor map with your own data in Mapbox GL JS](https://dev.to/mapbox/build-an-indoor-map-with-your-own-data-in-mapbox-gl-js-127m) — hands-on tutorial (metadata properties, `indoor` block, `IndoorControl`); a companion to the above, not a spec

## Feature model
`indoor.geojson` follows Mapbox's indoor data model ([guide](https://docs.mapbox.com/help/dive-deeper/indoor-mapping/)):
`facility` > `structure` > `floor` > `room`, linked by `facility_id` / `structure_ids` / `floor_id`; ids are unique across
buildings (`facility-<slug>`, `structure-<slug>`, `floor-<slug>-<level>` with `b1` for basements, `room-<slug>-<config id>`;
the config's own id stays in `room_id`). Floors carry `name` (1, B1), `description`, `z_index` (0 = 1F), `is_default` and
`conflicted_floor_ids` (all other floors); rooms carry `class` (indoor-v3 vocabulary where one exists, else our `category`);
each floor has an exterior `wall` (`type: room`, `class: wall`, `wall_height`). `z_offset` is the data model's (relative to the floor, so 0; the floor's height is its `ground_z_offset`); our `lift` is the
absolute metres above ground for the flat fill / walls. Our own keys (`level`, `floor_name`,
`category`, `base_height`, `height`, `color`, …) stay for tools and the floor-map overlay. Rooms with a sourced shape also get a point POI (`shape_type: poi`, `icon`): facilities (toilet / lift / stairs / ATM) by name or floor-map pictogram, and shops by category + name (`shop`, `restaurant`, `cafe`, `bank`; our own `hospital` / `pharmacy`, whose room `class` is `healthcare`) — `generate_geojson.shop_icon`. The preview uses Mapbox's own
indoor mechanism (Standard style + `indoor` block + clip layer + `IndoorControl` + `is-active-floor`; GL JS 3.32): the chosen
floor is drawn flat at street level with its exterior wall, and the panels follow IndoorControl through the (experimental)
`map.style.indoorManager` `selector-update` event. Config room ids
are what you edit; the build output and `selection.json` show `room_id`.

## Commands
- Setup: `python3 -m venv .venv && .venv/bin/pip install -r requirements.txt`
- Tests: `.venv/bin/python -m pytest -q`
- Example: `.venv/bin/python main.py build samples/building_config.json && .venv/bin/python main.py serve marubiru-sample`

Secrets and settings go in `.env` (git-ignored, loaded by `main.py`; template: `.env.example`; shell variables win).
Mapbox token: `$MAPBOX_ACCESS_TOKEN` (public pk.* token; embedded into index.html) or entered in the page.
OSM APIs: respect Nominatim's 1 req/s; footprints are cached in `output/<slug>/footprint_cache.geojson`.
